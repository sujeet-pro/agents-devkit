# `docs-commit-message` — workflow detail

## Phase 0 — prompt expansion

1. Resolve repo via `repos.md`.
2. Verify HEAD exists (`git rev-parse HEAD` succeeds; fresh repos
   without a HEAD commit are a special case — first commit is
   allowed but has no `git log -10` to detect convention from).
3. Pick slug: `commit-<YYYYMMDD>-<short-hash-of-staged>` where the
   short hash is the first 6 chars of `git diff --cached | sha1sum`.
4. Create `.temp/task-<slug>/`; write `prompt.txt`.

## Phase 1 — preflight

1. `git diff --cached --stat > diffstat.txt`. If the output is empty,
   stop with:
   ```
   No staged changes. Stage with `git add <path>` or
   `git add -p` first.
   ```
2. `git diff --cached > staged.diff`.
3. `git log -10 --pretty=format:%s > recent-subjects.txt` (if
   `recent-subjects.txt` is empty, this is the first commit —
   default to Conventional Commits unless the user passed `--style`).
4. Detect convention per `references/convention-detector.md`;
   record `style` in `.temp/task-<slug>/detected-style.txt`.
5. If `--style` is passed, it overrides the detection; note the
   override in the report.

## Phase 2 — draft

1. Parse `staged.diff` into logical chunks:
   - Group by file; group files by top-level directory.
   - Identify the "dominant change": biggest cluster of lines in one
     feature area.
2. Pick the subject:
   - Type: map the dominant change — bug keyword in
     `recent-subjects.txt` or diff → `fix`; new function / component
     → `feat`; rename / move / extract → `refactor`; test file only
     → `test`; `CHANGELOG.md` only → `chore`.
   - Scope: primary folder or feature (optional).
   - Verb: imperative mood (`add`, `fix`, `migrate`).
   - What: ≤ 72-char summary of the dominant change.
3. Write the body:
   - Paragraph 1: why this change — the user-visible problem, the
     motivating ticket, or the gap this fills.
   - Paragraph 2 (optional): why this approach — the alternatives
     considered, the trade-off picked.
   - Paragraph 3 (optional): notes for reviewers — e.g. "feature
     flag default is false; gradual rollout via Statsig gate".
4. Trailers:
   - Ticket refs from the branch name or diff comments, if they
     match the repo's ticket-ref convention.
   - `Co-authored-by:` only if the diff has authorship hints (e.g.
     `pair-programming` block comment) or the user asks.
5. Write `.temp/task-<slug>/commit-msg.txt`:
   ```
   <subject>
   
   <body>
   
   <trailers>
   ```

## Phase 3 — validate

Per `references/validator.md`:

1. Subject ≤ 72 chars.
2. Subject is imperative mood (no `-ed` / `-ing` endings on the
   leading verb; no trailing period).
3. Body paragraph width ≤ 72 (URLs and code fences excepted).
4. Blank line between subject and body; blank line between body and
   trailers.
5. If `--style conventional`: matches the regex
   `^(feat|fix|chore|refactor|docs|test|perf|build|ci|style|revert)(\([^)]+\))?(!)?: .+`.
6. No "generated by" / "AI-authored" footer.
7. No `--amend` or `--no-verify` hint in the message.

## Phase 4 — optional `--fix`

1. Re-show `commit-msg.txt` in the final response.
2. Ask once (even under `--auto`):
   ```
   Run `git commit --file .temp/task-<slug>/commit-msg.txt`? (y/n)
   ```
3. On yes:
   - Run `git commit --file .temp/task-<slug>/commit-msg.txt`.
   - Capture the resulting commit hash.
   - Run `git show --stat HEAD` and include in the report.
4. If the pre-commit / commit-msg hook rejects the message:
   - Surface the hook output.
   - Offer to re-draft (loop back to Phase 2) or stop.
   - NEVER retry with `--no-verify`.
5. On no:
   - Leave `commit-msg.txt` in place; the user can
     `git commit -F .temp/task-<slug>/commit-msg.txt` manually.

## Loop control

- If the validator fails 3× in a session, stop and surface. Usually
  the diff is too big or spans multiple logical changes — suggest
  splitting via `git add -p`.
- Never retry with `--no-verify` to get past a rejecting hook.
