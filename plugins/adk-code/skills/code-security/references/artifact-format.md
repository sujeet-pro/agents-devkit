# `code-security` — artifact format

## `.temp/task-<slug>/` layout

```
.temp/task-<slug>/
├── prompt.txt                                 # verbatim user prompt + ISO timestamp (sanitized)
├── threat-model.md                            # Phase 2 — exactly 5 lines
├── boundary.md                                # Phase 3 — input + output points
├── exploit-test.md                            # Phase 4 — failing test on HEAD + observed output
├── plan.md                                    # Phase 5 — mitigation plan
├── security-review.md                         # Phase 7 — security-reviewer agent findings
├── (optional) skill-plan.md                   # if called from /adk-core:auto
├── validation/
│   └── per-skill/
│       └── code-security.md                   # implementer + measurement evidence
└── report.md                                  # Phase 8 — final report
```

## Slug rules

1. Kebab-case. Often shaped `secure-<scope>-<symptom>` (e.g. `secure-search-sqli`, `secure-upload-validation`, `secure-cve-2025-12345`, `secure-login-rate-limit`).
2. 3-6 words.
3. Date-prefix only for disambiguation.
4. Generated by `bin/adk-task-slug`.

## Required artifacts (cannot skip even under `--auto`)

- **`threat-model.md`** with EXACTLY 5 lines (the model is what makes this skill different from `code-bugfix`).
- **`boundary.md`** identifying input + output / privileged-action points.
- **`exploit-test.md`** with the failing-on-HEAD output captured (the proof of vulnerability).
- **`security-review.md`** with the security-reviewer agent's findings.
- **`report.md`** with the red→green transition.

If any is missing at Phase 8, the validator fails.

## Sensitive content handling

`prompt.txt` may contain CVE IDs and high-level vulnerability descriptions; these are fine. Do NOT paste:

- Working exploit payloads (use a placeholder like `<malicious payload>` and link to the test file in the working tree where the actual payload lives — that file ships with the fix and is appropriate).
- Customer / production data that demonstrates the exploit.
- Internal credentials / tokens.

The `report.md` IS internal (under `.temp/`, gitignored), so it can include exploit details for the operator's records. The eventual commit message + PR description are PUBLIC and use generic descriptions.

## Disclosure-aware artifact handling

For active CVEs being fixed BEFORE public disclosure:

- The `.temp/` artifacts are local to the operator's machine; they are not synced anywhere.
- Commit message language uses generic terms ("input validation fix on /api/upload"; "rate-limit on login"; "CVE patch in @acme/auth", referencing the CVE only by ID once it's coordinated to disclose).
- The fix lands BEFORE public disclosure, BUT the disclosure timeline is the operator's call (per the org's coordinated-disclosure policy).
- The skill never auto-publishes a CVE record.

## Cross-skill compatibility

- When `code-security` is called as a follow-up to `/adk-review:audit-repo` or `audit-pr`, the audit findings are at `.temp/task-<slug>/audit/findings.md` (or similar; the audit skill's artifact). `code-security` reads them as starting context for one finding per task.
- When `code-security` is followed by `/adk-review:review-code-changes`, the review skill reads `report.md` + `security-review.md` + the diff. The review notes the security pass already happened (via security-reviewer agent in Phase 7) but does its standard pass.
- The security-reviewer agent (from `adk-review`) is invoked in Phase 7 of `code-security` itself — distinct from a final review-code-changes pass.

## Rules

1. Never write outside `.temp/task-<slug>/` until the user signs off (then the test files + mitigation are in the working tree).
2. `.temp/` is in `.gitignore`.
3. Do not auto-clean.
4. Slug preserved across the session.
5. The exploit test in the repo IS in the working tree — that's the regression test; it ships with the fix.
6. The 5-line threat model in `threat-model.md` is REQUIRED — no exceptions.
